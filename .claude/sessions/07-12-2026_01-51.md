## Project overview
NLLC is a SvelteKit + Web Audio live-coding music environment: a console of
`/`-commands plus a live mixer UI, both thin views onto one shared `NLLC`
engine instance (tracks/buses/master channels, processors, modulators,
patches, a lookahead clock). This session added a real persistence layer on
top of that engine — whole-session save/load to a file, plus named
in-memory states you can glide between with `/recall` — and reworked the
app's entry points around it: a homepage with real content (session links +
audio device/latency options) instead of a bare link, a blank `/code-editor`
instead of one with baked-in demo content, and a new `/code-editor/demo`
route for a first-run example. `svelte-check` is clean throughout.

**Nothing has been committed.** The working tree now has 27 modified files
plus 4 new paths (`session.js`, `SessionPage.svelte`,
`routes/code-editor/demo/`, `static/sessions/`) — this is on top of an
already-uncommitted backlog from the two sessions before this one (the last

## Known issues
- Headless Chromium in this sandbox still doesn't render real-time audio —
  all verification this session was console-text/DOM/file-download/
  file-picker based (Playwright), not live audio assertions. The `/recall`
  fade timing and ramp curves are correct by code inspection + the
  `AudioParam` scheduling model, not by ear.
- `/recall`'s fade choreography only smooths *channel gain* and *patch
  depth* on appear/disappear — a processor or modulator that's
  added/removed during a recall pops in/out instantly (no fade), and sends
  swap instantly too. This was a deliberate scope call (documented in
  `session.js`), not an oversight, but worth knowing if a recall sounds
  more abrupt than expected for a heavily-processed channel.
- The homepage's "Show device names" button requests microphone permission
  as the standard (if slightly surprising) browser workaround for revealing
  audio *output* device labels — there's a code comment explaining why, but
  it's worth knowing before someone reports it as a confusing permission
  prompt.
- `AudioContext.setSinkId` (output device switching) isn't supported in
  every browser yet — the homepage feature-detects this and disables the
  selector when unsupported, but it hasn't been tested against a real
  non-default output device on hardware, only that the code path doesn't
  throw.
